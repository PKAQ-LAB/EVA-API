# EVA 后端开发顶层规则

用户确认：2026-11-05；合并更新：2026-11-07。适用于 EVA-API 本体、Template-API 及其衍生后端。

## 适用边界

- 本文合并既有开发规则与用户在会务开发中确认的补充要求，同一事项以本文和用户后续明确要求为准，不重复维护冲突版本。
- EVA-API 本体在 `cornerstone` 分支开发，使用自身 `org.pkaq` 根包和既有 domain/service 模块；衍生项目使用自己的分支、根包和业务模块，不强制复制本体子模块数量。
- 规则约束今后新增及任务涉及的代码，不代表历史代码已经全部验收，也不自动授权跨仓重构、数据库迁移、构建、服务启动或发布。
- 不把会务项目的 `com.jmsk`、`api-meeting`、`mt_` 前缀、关闭租户及权限、RustFS 桶名、身份逗号存储、文本会议时间或联调验证码推广为框架默认值。实际业务以当前项目确认的模型和配置为准。
- 本文与 AIBrain 的 `04-Rules/后端规则/eva-api-development.md`、Template-API 的 `docs/DEVELOPMENT_RULES.md` 同步维护；表命名专门规则见 AIBrain 的 `eva-api-table-naming.md`，不变更其适用边界。

## 1. 设计原则

1. 开发前先读当前框架实现、`sys` 对应模块和项目规则，理解已有设计，不凭印象重写一套。
2. 以适用性、正确性和简洁性为先，不为表面一致机械套用框架，也不擅自偏离框架已有能力。
3. 不过度拆表、拆包、拆 Service 或 Mapper；仅在职责、实际复用或复杂度需要时拆分。
4. 不确定的业务语义、契约和设计取舍先与用户讨论；已明确的要求直接执行，不反复确认。
5. 框架问题在框架层修复并验证；需要更新依赖时发布新版本，由业务项目明确升级，不在各项目重复打补丁。

6. 修改前核对 Git 状态和调用影响，先理解上游行为；不覆盖无关修改。已有授权直接执行，不因流程文档重复索要授权。
7. 未经授权不提交、推送、发布或执行破坏性操作；确立规则本身不授权存量重构和数据库迁移。

## 2. 模块、包与分层

1. 按业务模块分包，一个模块一个业务包，包内按实际职责组织 `ctrl`、`bo`、`vo`、`entity`、`service`、`mapper`、`convert`；不存在的职责不建空包。
2. 子表、关系表与所属主表放在同一业务模块，不为每张表单独建立一套业务包。
3. Controller 只负责接收参数、触发校验、调用 Service 和封装响应；不得直接调用 Mapper 拼接查询、统计、分页或执行业务流程。
4. Service 承担业务编排、查询条件处理、保存和事务边界；Mapper 承担持久化访问。
5. Controller 将查询 Bo 整体传给 Service，由 Service 拆解查询条件，不在 Controller 中逐字段拆解并组装业务结果。
6. 相同模块的请求前缀保持一致，沿用项目现有 `/list`、`/get/{id}`、`/edit`、`/del` 等契约，不为命名规则擅自修改 HTTP 路径。
7. 分页沿用当前框架的 PageBo、分页参数解析及分页结果机制。业务条件进入 Service，不重复手写 `offset`、列表 SQL 和 `count` 来替代已有分页能力；确需特殊分页时说明原因。
8. 本体已有 domain/service 契约边界时保留；衍生项目按实际规模组织，不仅为仿照本体而新增 Maven/Gradle 子模块。

9. 已有 domain 模块只放 Bo、Vo 和服务接口，基础契约依赖 eva-core-contract；Controller、Entity、Mapper、Convert、SQL 及数据库实现放在 service 模块，不为契约引入持久化实现依赖。
10. 认证、系统管理、数据访问保持各自边界，通用实现替换优先小型接口，不恢复复杂 supporter 体系。

## 3. Bo、Entity、Vo 与转换

1. 查询条件使用独立查询 Bo；已有 PageBo 时按框架方式扩展，不在接口中铺开大量查询参数。
2. 多字段 JSON、表单及上传请求建立独立 Bo，不在 Controller 内声明临时 `record` 或内部请求类。
3. 单个简单参数可直接接收，不仅为包住一个值建立无业务意义的 Bo；统一契约确有需要时再使用 Bo。
4. 返回业务数据使用 Vo，不将持久化 Entity 直接暴露给前端。
5. 按实际模型复用 StdEntity、基础 Bo、Vo、Ctrl、Service 等契约；创建修改信息、版本等公共字段不重复定义，不为继承引入不适用行为。
6. Bo、Entity、Vo 的同义字段以数据库已确认的业务字段为基准，前后端保持一致。备注、说明、其他描述等备注性内容统一使用 `remark`，不另造 `notes`、`content` 等别名。正文等独立业务内容保留自身字段。
7. Bo—Entity—Vo 的模型转换使用 MapStruct，沿用项目 Convert 与 MapConvertConfig；不在 Service 中堆积构造器参数和逐字段复制代码。
8. 同名同义字段使用自动映射，不写重复的 `@Mapping`；不额外把 null 转成空字符串，前端处理展示空值。存在真实语义差异时才显式转换。
9. Bo、Vo 是否使用 record，按不可变性、继承、框架绑定和映射兼容性选择，不一律改成 record，也不一律否定 record；需要继承或可变绑定时使用普通类与 Lombok。
10. 简单 getter、setter、构造器使用适用的 Lombok 注解；依赖优先 `@RequiredArgsConstructor` 配合 `private final`，不手写只有字段赋值的构造器。

11. Entity 只负责持久化模型，不添加 Swagger 展示注解；表映射和 MyBatis 别名按实际配置准确声明，不机械添加可由命名策略推导的重复映射。

## 4. 数据库与字典

1. 表名按项目业务前缀、模块和业务对象组织；主从明细子表以 `_line` 结尾，关系表以 `_ref` 结尾。分类依据业务职责，不仅凭关联字段判断。
2. 主表、子表、关系表在设计文档和包内归组呈现，不把相关表分散到无关模块。
3. 子表指向所属主记录的字段使用 `main_id`；关系表的其他关联对象使用能表达业务含义的字段，不将多个不同关联字段都叫 `main_id`。
4. 复用基础字典表及其编码机制，不为每类字典另建业务表；业务字典值按已确认的六位数字编码规则设计，保留编码语义，既有框架保留码不擅自改写。
5. 集合采用关系表、明细表还是逗号分隔字段，应依据查询、约束和维护方式确定。用户已确认的简单编码集合不得再额外建立重复关系表，也不得把逗号分隔推广为所有关系的固定方案。
6. 字段类型、长度及必填性以实际业务和已确认表设计为准，不为方便统一放大长度；校验约束与数据库一致。
7. 日期、时间字段按实际语义选择类型。允许“计票结束后”等文本的时间才使用文本字段；不把某个前端控件返回字符串作为所有日期改成 VARCHAR 的理由。
8. 不臆造历史兼容字段、资格状态、冗余身份说明和附件摘要等业务未要求的字段。
9. 图片存对象存储，业务表只保留业务需要的对象标识或访问地址；不重复存储不需要的 MIME、字节数、SHA256 等信息。
10. 表设计文档只维护一份当前稿，先给总表目录，按主表、子表、关系归组展示；字段信息已说明的内容不重复写解释。设计未定稿前不提前生成执行 SQL。
11. 数据库外键是否启用属于项目设计决定，不把当前项目“不建物理外键”直接升级为框架通用禁令。

12. 在用户明确宣布正式发布之前，Flyway 只保留一个初始化脚本，结构和预置数据变更合入该脚本；不得因此自动重跑现库初始化、重建数据库或改写 Flyway 历史。现库调整按已授权范围执行。
13. 既有 9999 只读记录由后端保护，主记录的保护覆盖其明细和关系；树形数据防止循环引用、重复追加和非法换父。

## 5. MyBatis-Plus 与 SQL

1. 常规增删改查和条件查询优先使用 MyBatis-Plus 及 Lambda 表达式，不另用 JdbcTemplate 绕开已有持久化体系。
2. 复杂查询、必要的条件更新或并发写入 SQL 放到 Mapper 对应 XML 中，不在 Java 注解、Controller 或 Service 中拼写 SQL。
3. 沿用框架分页拦截器和实际的分页契约，查询条件在 Service 中组织，Mapper 接收持久化所需参数。
4. 已由框架处理的租户、逻辑删除和默认排序，不在每次 Lambda 查询中重复添加；写自定义 XML 时必须核对哪些行为仍会自动生效，不能直接删掉必要条件。
5. 复用实体表映射与命名策略。明确映射、别名确有需要时才声明，不重复添加可由现有配置准确推导的映射；不得因 PostgreSQL 非引号标识符不区分大小写而改写真实物理表名。
6. XML SQL 保持可读：查询或写入语句起始关键字后换行，字段或赋值每项一行；`FROM 表名` 单独一行；`WHERE` 单独一行，每个条件一行；JOIN、ORDER BY 等按语义独立排版。
7. 不添加无意义的 CDATA；只对 XML 保留字符做必要转义。
8. Mapper 配置按实际需要保留，不机械添加 `affectData`、`flushCache`、`useCache` 等属性；结果类型或数据变更语义确有需要时不能为精简而删除。

```sql
SELECT
    id,
    name,
    remark
FROM mt_example
WHERE
    main_id = #{mainId}
    AND deleted = 0
ORDER BY
    sort,
    id
```

示例只演示排版；业务 SQL 是否需要逻辑删除条件，以实际拦截器行为为准。

9. SQL 与真实字段、类型处理器和返回模型一致；必要的结果映射必须验证，不能依赖未经验证的隐式字段回填。

## 6. 事务、并发与框架自动能力

1. 主表与子表、关系记录的联合写入在 Service 建立事务边界，保持整次业务操作一致。
2. 创建人、创建时间、修改人、修改时间及逻辑删除等，沿用框架自动填充，不重复手工设置。
3. 不为每次保存默认添加 `SELECT FOR UPDATE`、手工锁主表、重复查询或额外幂等收据表。
4. 事务保证原子性；乐观锁和数据库唯一约束按实际冲突场景使用。不能声称有事务就解决所有并发问题，也不能无场景地到处加锁。
5. 只有明确存在重复执行、抢占或冲突风险的流程，才设计额外并发控制，并说明保护的业务不变量。
6. 租户、资源权限和数据权限遵循项目配置；关闭的能力不额外手工补上。框架权限开关关闭后，相关读取、写入和日志检查也必须遵守开关语义。
7. 不在业务 Service 中到处复制 `requireAdmin()` 之类的角色判断，优先复用框架认证授权；真正的业务操作资格仍按已确认需求处理，不能把菜单隐藏当成服务端认证。

8. 启用 schema 租户隔离时，schema 名来自校验后的 tenant code，不拼接未校验输入；主键 ID 保留，tenant code 的变更评估 schema 及关联影响，不把这一模式强制套用到关闭租户或行级隔离项目。
9. 认证、模块、接口资源、按钮和数据权限分别落实；已有前端权限契约使用菜单下无前缀 resources key 数组及 Umi Access，read 表示详情读取，模块 path 使用真实路由，不用数据库 ID 拼路由。
10. 数据权限关闭时不做范围过滤，相关页面不展示权限配置；开启时指定部门用部门树、指定岗位用岗位多选并正确回显。岗位准入只赋予符合范围的数据读取资格，不自动赋予编辑和删除权限。
11. 角色、资源、岗位和授权变更按现有机制使缓存失效，不让旧会话继续使用已撤销权限。登录日志、错误日志和业务日志按各自归属和访问规则处理，业务日志必须来自真实操作。

## 7. 校验、异常与接口说明

1. Validator 注解必须配置 message，沿用统一文案键，并与实际表字段和业务约束一致。
2. 不重复判空，不为已由同一边界覆盖的条件重复添加检查；不为删除 ID 无差别增加 `@Positive`，不默认给批量删除列表元素叠加不需要的判空。
3. 校验服务于真实输入约束，不扩展成大量无业务场景的防御判断；必要的认证、数据约束和完整性检查仍须保留。
4. 业务异常通过模块 Codes 类及框架规定的 `newException()` 等方式抛出，文案集中管理；不在业务代码里散落 ResponseStatusException 和硬编码提示。
5. 不添加只为包住正常流程的 try/catch，不吞异常、不重复包装已可由统一异常处理器处理的异常。
6. Controller 配置 OpenAPI/Swagger 接口与参数说明，按项目提供 SwaggerConfig 分组；分组名使用具体系统业务名称，不将“电子会务”固定为框架默认名。
7. 接口请求地址、请求响应字段和文案契约前后端统一管理，不通过临时别名、硬编码地址掩盖契约差异。

## 8. 命名、注释与排版

1. 类使用大驼峰，方法及变量使用小驼峰，常量使用大写下划线，包名全小写；命名表达业务含义。
2. 单条查询使用 `getXxx`，列表及分页查询使用 `listXxx`；保存、删除等采用动作加业务对象。框架重写方法保持签名兼容，不能为了改名破坏继承。
3. 方法前添加多行中文 JavaDoc，简短、口语化地说明用途；不重复解释方法名已经清楚表达的机械细节。
4. 成员变量、Entity 属性前使用单行中文注释说明含义，字段之间空一行，不省略依赖字段的说明。
5. `if`、`for` 等控制结构前添加简短中文注释，说明本段判断或循环的用途，避免逐字翻译语法。
6. 变量声明、条件判断、循环和返回等语义段之间留空行；连续同类语句按语义分组，长表达式和参数换行。
7. 注解和类型通过 import 引入，不在代码中铺完整包名；避免通配符 import。
8. 注释只说明当前真实设计，不保留无用说明、过时代码、旧模块名或模板品牌文案。

9. 代码使用 UTF-8、LF、四空格缩进及不超过 120 字符的行宽，控制语句使用大括号，不在 getter 中修改状态。
10. 服务接口按本体现有约定使用 I 前缀，控制器使用 Ctrl 后缀，模型和转换器使用对应 Bo、Vo、Entity、Convert 等后缀；不照搬现有拼写错误。

## 9. 依赖与配置

1. 新项目只保留所需启动模块与业务模块，复用已发布基础依赖，不复制整套框架源码。
2. 依赖坐标、版本和插件版本集中放到 `gradle/libs.versions.toml`，构建脚本通过版本目录引用。
3. 先核对实际传递性依赖与插件行为，不重复声明已提供且可用的 common、mybatis、Lombok、MapStruct 等依赖；编译类路径或注解处理器确需独立声明时保留并说明原因。
4. 私服认证按项目已经确定的配置方式使用，不增加无意义的存在性判断和备用分支；凭据不写进通用规则、示例或日志。
5. 基础功能和自动能力优先复用框架，业务差异留在业务模块；通用缺陷修复后发布新依赖，不覆盖既有正式版本产物。

## 10. 验证与交付

1. 按模块逐项完成；修改范围内先编译，再做适当的定向测试或 curl CRUD 验证，不为了简单验证强行新增测试工程。
2. 涉及数据库、分页、权限开关或文件上传时，验证真实行为，不以编译通过代替接口联调。
3. 接口开发、前后端对接、打包和发布分别遵循当前授权，不把完成接口视为已完成客户端对接。
4. 提交、推送、依赖发布分别核实结果，不能把本地提交说成已推送；保护无关修改和凭据，不批量暂存。
5. 交付说明区分本次问题、既有问题、环境阻碍和未验证项，不把静态检查称为运行时验收。
